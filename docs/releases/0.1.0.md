# PartitionGuard 0.1.0 candidate

**Status: public source; package release candidate maintained by André Barrocas.**

PartitionGuard safely plans, executes, recovers, and verifies changes to production data products. This initial candidate targets one concrete procedure: add a replacement representation, backfill a selected historical date range, recover interrupted batches, and accept the result only after deterministic verification.

## Included

ODCS subset loading, deterministic compatibility/risk reports, declared downstream impact, typed migration plans, bounded workloads, dry-run preflight, exact-plan approval, a hash-linked execution ledger, checkpoint reconciliation, and mandatory verification are implemented. DuckDB and PostgreSQL handle relational storage. Local Delta Lake adds native commits, physical partition boundaries, read-only historical snapshots, and conflict detection.

An offline OpenLineage importer accepts dependency information without building a catalog. Experimental AWS support covers bounded, read-only S3 inventory and Glue schema inspection. AWS request/limit behavior is stub-tested; no live cloud integration run or AWS migration execution is claimed.

Tests cover failures before and after commit, stale approval/source drift, replay
without duplicate data, corrupted migration results, strict numeric conversions,
required checks and plugin selection. CI tests Python 3.11–3.13 with PostgreSQL 16.
The [validation report](../validation.md) records dated observations and links
to remote results. Run `python examples/showcase.py` to exercise recovery,
verification and repair through the public CLI using disposable synthetic data.

## Scope of a completed run

`COMPLETE` means this approved bounded additive stage passed its required policy. It does not mean every producer has adopted dual writes, every consumer has migrated, all historical dates were included, or the old field may be removed. Those changes require separate coordination and review. Plans for unsupported destructive operations are blocked.

## Known limits

- Relevant writers must be stopped. No universal online-concurrency or exactly-once guarantee is offered.
- The initial contract loader implements a documented ODCS subset and refuses unsupported safety requirements.
- Type changes use a narrow tested conversion matrix. In-place type conversion, arbitrary expressions, and precision-specific nested types are unsupported.
- Delta supports local tables with physical DATE partitions. Matching files can be rewritten. A committed Delta action cannot be rolled back by the Python transaction context.
- Original-row fingerprints require bounded row reads; this candidate has not established production-scale throughput.
- No AWS execution, broad catalog integration, hosted control plane, LLM safety decision, or Rust performance extension is included. Read-only AWS inventory remains experimental.
- Package naming was checked during development but must be rechecked and reserved by the owner before publication.

## Maintainer release gate

Before publishing, run the full suite with a real PostgreSQL database and Delta dependencies, regenerate tutorial evidence, build/install the wheel, build documentation, review the limitations, and configure repository ownership, private reporting, GitHub environments, and PyPI trusted publishing. The manual release workflow checks the version/tag and produces a draft release; public publication requires the owner's deliberate action.

Real user trials and external security review remain follow-up work. A green test suite is evidence of tested behavior, not proof of general production suitability.
